# 0003: Check findings and completeness

Esdieff reports errors, warnings, incomplete checks, and [check coverage](../../CONTEXT.md#model-work) separately. Missing definitions, unsupported checks, unresolved interpretations, or unknown critical features can leave conclusions undetermined; they do not by themselves establish a definite RFC violation. A definite error remains reportable alongside incomplete checks only when the missing information cannot change that conclusion.

This distinction supports phased implementation without presenting unassessed requirements as satisfied. In particular, [RFC 9880, Section 3.1](https://www.rfc-editor.org/rfc/rfc9880.html#section-3.1) requires understanding critical features for proper processing; a base-only interpretation cannot establish conclusions that depend on unknown critical semantics.

A successful requested assessment completes all explicitly requested checks without errors. Warnings are nonblocking by default, with an optional stricter policy. Requested unsupported requirements remain incomplete; Esdieff cannot silently narrow an assessment to implemented checks. Human and JSON reports carry equivalent conclusions, scope, coverage, and incompleteness, and distinguish effective-model paths from available source locations.

During phased delivery, the default is a named initial [assessment profile](../../CONTEXT.md#model-work) with a predetermined requirement inventory. Every check summary identifies the broader RFC coverage, including when the requested initial assessment succeeds. A complete recorded-baseline assessment can be requested explicitly; unsupported requested requirements leave it incomplete. The initial inventory and exclusions are a product contract to settle before implementation, rather than a reflection of whichever checks happen to exist.

Coverage expansion aims at comprehensive base-SDF model checking while permitting explicit deferrals for uncommon cases. Each [Deferred model check](../../CONTEXT.md#model-work) records the affected requirement, current assessment outcome, reason and condition for reconsideration. Deferred capabilities retain their coverage obligations; unresolved interpretations and requirements needing external knowledge remain distinct from missing implementation. Broadening capability does not silently redefine the Initial assessment or remove requirements from the Full inventory established by [ADR 0011: Machine-readable report contracts](0011-machine-readable-report-contracts.md).

Deferral reasons and reconsideration conditions belong to the documented capability boundaries. Scheduling work does not change its reported assessment status: deferral is planning information, not another runtime status or an additional report field. Reports retain their existing assessment states and explanations of unavailable conclusions.

An unfamiliar unqualified Quality Name receives a warning to help detect vocabulary mistakes. Recognized but unsupported optional extension vocabulary receives informational notices. Initial and expanded assessments summarize these observations. Full names and locates each inspected occurrence so the author can find unsupported content behind unfinished requirements. Composed observations retain the effective position and nearest source contribution. Existing diagnostic limits bound the retained details without changing coverage states. Permitted extension content is retained. Undeclared extension vocabulary leaves base conclusions intact under [ADR 0037: Undeclared extension vocabulary](0037-undeclared-extension-vocabulary.md), and only conclusions that need an extension's own unsupported meaning remain incomplete. Explicitly rejected historical vocabulary follows [ADR 0008: Reject the historical Action input quality](0008-reject-historical-action-input-quality.md).

Provably empty permitted value sets receive explanatory warnings rather than being classified automatically as RFC violations. These checks begin with simple proved cases and report the contradiction classes assessed; they do not promise general satisfiability analysis. Applicable null and choice semantics follow [ADR 0005: Nullability and presence](0005-nullability-and-presence.md).

## Considered Options

A single pass/fail result would conflate invalid models with models whose checking could not finish. A simple report may summarize the outcome, but it must preserve findings, incompleteness, and the scope actually assessed.
