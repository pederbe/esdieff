# Public workflow and report contract

This text specifies the shared guarantees behind the library, command and JSON report. The reasons are [ADR 0010: Domain-oriented library and caller simplicity](adr/0010-domain-oriented-library-and-caller-simplicity.md), [ADR 0011: Machine-readable report contracts](adr/0011-machine-readable-report-contracts.md), and [ADR 0012: Exact numbers and JSON input policies](adr/0012-exact-numbers-and-json-input-policies.md). Domain terms follow [the domain language](../GLOSSARY.md). Standards semantics come from [RFC 9880 Sections 4.4 and 4.7](https://www.rfc-editor.org/rfc/rfc9880.html#section-4.4), [RFC 6901 Sections 3 and 4](https://www.rfc-editor.org/rfc/rfc6901.html#section-3) for pointer tokens, and [RFC 7396 Section 2](https://www.rfc-editor.org/rfc/rfc7396.html#section-2) for merge/deletion. Resource limits and report fields are toolkit contracts, not RFC limits.

## Library work and ownership

The public boundary is document-supplied domain work. A `Catalogue` owns each supplied source's identity, acquisition result and content. Construction accepts owned content, or converts borrowed caller content into owned storage once. Views borrow the catalogue/result; callers do not keep the original strings alive, own reference graphs, manually merge JSON, or expose a particular parser/numeric dependency. Internals may use immutable sharing and caches, but do not expose mutable checked state.

The library operations include `Catalogue::check`, `inspect`, `source`, `effective`, `check_sample`, `generate`, `check_trace`, `reference` and `export_schema`, plus `AuthorRequest::author`, `EditRequest::edit` and `ComparisonRequest::compare`. They reuse the source and effective-model foundation, with operation-specific results and report formats. Requests use builders with private fields. Operations produce usable results alongside scoped conditions. Malformed source input, unavailable dependencies and exceeded admitted work budgets are domain results. Configuration errors, unknown selectors and hard ceilings that prevent complete plan/request admission are request errors. Neither is a panic contract.

Each acquisition attempt receives a unique request-local `SourceId` before reading. Identity is an opaque caller key, distinct from a bounded display label, optional acquisition URI, content identity and SDF namespace. Duplicate caller keys are request errors. Same bytes supplied twice are two contributors, with no deduplication or precedence. CLI paths have distinct explicit identities; input position is not a semantic role. Source content is immutable owned bytes; UTF-8 text is available if decoding permits it, and raw bytes remain inspectable after decoding failures. Partial read/size-limit content records retained bytes and `content_complete:false`; it never purports to be the whole source. Acquisition failure has no content and stays visible. An optional caller content-version token is opaque; no path or label is a content hash. Reproducible callers may provide a digest; mandatory library hashing is not required.

Before copying any caller metadata, request validation checks UTF-8 byte lengths: caller key at most 256, display label 512, optional acquisition URI 2,048, content-version token 128 and digest 256. It preflights all attempts together against 1 MiB combined caller metadata, including exact raw filesystem identity bytes, every repeated source/scope-reference representation and all model, sample and generated attempts. These roles share one ceiling of 256 source attempts. Internal/report `SourceId` is a compact nonzero u32 allocated per request; it is separate from the bounded unique caller key. UTF-8 keys compare exactly, without case folding or normalization. Raw filesystem identities can contain non-UTF-8 bytes and are retained exactly for acquisition; their bytes consume the combined metadata budget. CLI adapters use bounded opaque caller keys to associate these identities, rather than forcing raw path bytes into UTF-8 keys.

Oversized semantic keys, URI/version/digest metadata, or aggregate metadata are request errors before ownership/copying or model processing. Keys/version identifiers are never clipped to fit. Only a display label may be shortened or omitted for presentation with a structured `label_omitted` reason; its full accepted form can remain available in owned metadata. Oversized supplied labels are request errors unless the caller explicitly requests label omission before retention. Library-owned baseline, policy and inventory metadata share a 64 KiB request budget. The mandatory report envelope is reserved before work using worst-case JSON escaping (up to six output bytes per input byte), all accepted source counts, fixed field overhead, repeated source/scope references, outcome/coverage counters and omission records. A report configuration smaller than that reserve is rejected before copying or acquisition. Optional report details consume only the remaining budget. No source attempt, aggregate finding or semantic identity is erased to meet a small report budget.

The default request has catalogue scope, including all supplied definitions and all source attempts. Explicit selected scope contains a nonempty set of supplied `SourceId` roots. Other sources are lookup candidates; reports separately identify roots, needed dependency sources, independently assessed sources and unavailable required sources. A missing/failed root is incomplete; an unreadable unrelated candidate remains in `sources` without alone spoiling selected-model work. If inability to inspect a candidate prevents establishing a needed addressed contributor or ambiguity, that lookup is incomplete. No implied network fetching or first/last input preference applies. Selected scope is rooted in documents, not individual definitions.

Selected checks independently assess their roots and use the shared effective evaluator for surviving imported content. Dependency source membership does not promise independent assessment of every definition or Information quality in that source. Catalogue checks do independently assess all sources. Global target discovery uses exact decoded namespace text and decoded target-pointer identity after the needed critical-feature context is established, as [ADR 0023: Supplied global composition and dependency scope](adr/0023-supplied-global-composition-and-dependency-scope.md) specifies. Possible contributors with unavailable identity remain distinct from established dependencies.

Source views expose retained JSON and raw content independently of effective work. Acquisition and decoding limits can still leave selected content unavailable. Typed source projections distinguish malformed/unsupported fields from absent fields. Effective views expose sdfThing, sdfObject, Property, Action, Event, Context and sdfData definitions with role-specific grouping, affordance, input/output and data-description access. Context retains its recorded draft scope. Callers can traverse groupings, inspect required declaration relationships, obtain effective Property capabilities, data types and constraints, choices/enum alternatives, declared defaults and opaque qualities without rebuilding their semantics. Map-data `required` remains separate from declaration `sdfRequired`. Extended data types remain tagged known/extended/undetermined values, not guessed base types.

An effective definition handle is scoped to its owning result and points to a root-document/effective path. Available subviews remain usable if another subview is incomplete. Missing, present, deleted and unavailable are distinct outcomes. Known defaults are returned as effective semantic values with a default origin when established; source access does not insert them. A lookup supports `Lookup::Found`, `NotFound`, `Ambiguous`, and `Unavailable`, so uncertainty cannot be mistaken for absence. Domain accessors return `Field::Absent`, `Present(T)`, or `Unavailable(reason)` as appropriate. `Option<T>` is reserved for an established optional absence.

The implemented effective owner is `EffectiveModel`, returned by `Catalogue::effective(EffectiveRequest::new(source_id).pointer(selector))` or borrowed from `Report::effective_model()`. It owns compact derived records and borrows immutable catalogue sources; its views borrow that owner. Effective named collection rows are `(name, Field<handle>)`, preserving known unavailable entries and accessible siblings without changing source iterator item types. A containing handle can retain independent subviews when one descendant is unavailable. Unknown needed identity makes the affected collection or lookup unavailable.

`explanation(pointer)` describes composed content and its nearest source, inheritance, override or deletion contributors. `default_explanation(pointer)` separately describes an established implicit semantic value without an authored contributor. Both can describe the same absent path: a null patch deleting inherited `writable:false` retains a Deleted content explanation and a Default explanation for the typed `true` capability. No defaults are inserted into JSON. Direct-item defaults and copied requiredness in full data descriptions remain scoped limitations, with raw syntax accessible. These guarantees follow [ADR 0020: Owned effective views and nearest origins](adr/0020-owned-effective-views-and-nearest-origins.md).

`Explanation::consumer()` returns the established importing source `sdfRef` as an optional immutable source view. Ordinary source content has no importing consumer. An outer consumer survives its mandatory target-root chain; separately composed nested references establish their own consumers. Human inspection and optional JSON `consumer` locations expose the same boundary without changing nearest content origins or fabricating authored default sources.

Checks evaluate independent source definitions and surviving effective vocabulary through one role and rule set. Distinct composed observations contribute to aggregate findings before detail retention. Unchanged local replay requires completed source evaluation, identical established role and clear feature context, and unchanged rule premises; traversal still reaches composed descendants. Initial and expanded source `extension.optional_unsupported` summaries count actually inspected source occurrences in `observed_occurrences`. Their effective summaries retain that code and basis but omit the source-only count. Condition, byte and pointer presentation limits leave semantic totals and requested-unit status unchanged.

Full reports retain `extension.optional_unsupported` per inspected occurrence,
with its decoded Quality Name in `arguments.quality` and its source location as
primary. A composed observation has its effective position as primary and the
nearest source contribution as one related location. `quality.unfamiliar`
conditions also carry `arguments.quality`, in every assessment. Human reports
show the name separately from the pointer, so it remains visible when a pointer
is omitted. These details identify unsupported content behind unfinished Full
requirements without changing its severity, interpretation or coverage status.
Full optional notices count occurrences rather than summaries. Each source
notice keeps `observed_occurrences: 1`; effective notices omit that source-only
argument. Existing condition and diagnostic-byte limits bound how
many occurrences are retained. Existing pointer limits omit pointers with their
structured reason, and the name is charged against the diagnostic-byte limit
before retention. No additional location collection or independent limit is used.

Accessible JSON has an Esdieff wrapper providing JSON kind, map/array traversal, scalar access and bounded generation. It retains arbitrary JSON numbers as numbers. No `serde_json::Value`, decimal-library type or mutable graph escapes into the public contract. Opaque structural access does not prove unknown extension meaning or permit generic edits to checked state.

## Numbers and locations

An exact numeric view exposes its accepted original JSON lexeme, mathematical sign/integrality and budgeted exact ordering. Explicit checked machine conversions may return not-representable; they never round silently and cannot replace exact access. Comparison and later equality have their own finite-work result. The public number type is independent of its private representation. Unchanged generated numbers preserve an accepted raw lexeme, including `10e1000000` and `1e-1000000`. A normalized internal coefficient is not a mandatory emitted token. Exact access to a count such as `18446744073709551616` establishes mathematical information, not normative CDDL `uint` membership, as ADR 0012 requires.

Locations are tagged source, effective or sample locations. A source location contains `source_id`, an optional decoded RFC 6901 pointer, and an optional half-open UTF-8 byte span. Byte spans refer to the retained original source, including key/token spans where relevant, and are not recomputed offsets in generated JSON. A root pointer is the empty string. Failed acquisition has a source identity with no invented pointer/span. A sample location uses its separate sample-source identity and pointer/span. An effective location contains the selected root identity and effective pointer; it is not a claim that this path exists in a supplied source. Non-renderable paths have `pointer:null` and a structured omission reason, with available spans retained.

An available explanation identifies the effective target, explanation kind (`source`, `inherited`, `override`, `deleted`, or `default`) and relevant source location(s). It may identify only the nearest contributor and patch location; it does not promise a complete history. `Unavailable` is explicit. For Device.ambient's temperature minimum, the effective path ends `/minimum`, with the Temperature source `/sdfData/Temperature/minimum`. Its maximum 100 points to the patch source `/sdfThing/Device/sdfObject/ambient/sdfProperty/temperature/maximum`. The removed description's explanation targets effective `/sdfThing/Device/sdfObject/ambient/description` despite the quality's absence, identifies deletion at the null patch source and, when available, the inherited Sensor description. Controller.level inherits minimum from the supplied Level document, while maximum 80 and removed description refer to the Controller patch. Explanations of relocated content keep their nearest content origins, and their importing consumer is the original authored reference, following [ADR 0036: Copied reference relocation](adr/0036-copied-reference-relocation.md).

An established Boolean default explanation additionally carries optional `default_value:true`, with the same value shown in human output. The field is absent for other origin kinds. It covers the already-supported Property readable/writable/observable and full-description nullable defaults, preserves separate deletion and default rows, and adds no JSON quality or interaction value. Detail admission reserves the annotation before construction; omitted explanation rows keep an explicit reason and do not erase typed characteristic access. This additive 1.x field follows [ADR 0022: Scalar constraints and characteristic states](adr/0022-scalar-constraints-and-characteristic-states.md).

Effective inspection additionally reports optional `result.alternatives` owner records with an effective owner location and collection `state` of `absent`, `present` or `unavailable`. Present can be empty. Known `branches` retain an `id` tagged `choice` with name or `enum` with occurrence index; branch states are `available`, `partial` or `unavailable`, with independent `complete`, `json_present`, optional unavailable reason and nearest/default/consumer explanations. A partial branch's derived `json` can retain opaque raw quality values while `unavailable_qualities` explicitly identifies unestablished meanings. Raw JSON is not sample admission or consistency evidence. The composed `result.json` and existing pointer selectors retain their meaning. Count, byte, pointer or work omissions use explicit reasons and never imply an absent collection or completed meaning. Human output exposes the same collection, branch and unavailable-quality distinctions. These additive fields deliberately retain emitted check/inspect version 1.0 and follow [ADR 0024: Effective alternatives and nullable characteristics](adr/0024-effective-alternatives-and-nullable-characteristics.md).

## Required declaration relationships

Requested required-declaration inspection adds `result.required_declarations` to the existing inspect1.0 result. Its twelve mandatory fields are `state`, `complete`, `unavailable_reason`, `owners_known`, `owners_retained`, `references_known`, `references_retained`, `targets_known`, `targets_retained`, `owners_omitted`, `traversal_complete` and `owners`. Counts describe discovered work and retained or presented subsets; no total of undiscovered owners is inferred. `available` with completed empty owners differs from `unavailable`, while a retained unfinished traversal is `partial`. Known invalid findings can coexist with complete traversal. Optional owner rows separate source and effective locations, relationship status, importing consumer and target capability (`established`, `partial`, `unavailable`, `not_requested`). Missing targets produce the Advice notice `required.target_missing` and scoped incompleteness; established wrong roles and malformed syntax are independent RFC errors. This inspection keeps the one existing inspection unit and the initial assessment inventory unchanged, following [ADR 0026: Required declaration relationships and source evidence](adr/0026-required-declaration-relationships-and-source-evidence.md).

The requested operation admits the existing mandatory envelope plus twelve times selector bytes plus 1024 bytes before semantic work. The same additional reserve is subtracted from optional wire and scratch allowances. The summary is emitted directly into the existing output buffers with exact decimal Counts, fixed printable ASCII reasons of at most 96 bytes and quote/backslash escaping. It creates no summary `Value`/map, owned escaped text, numeric string, redundant selector flag or hidden empty owner transport DTO. A fixed Counts record occupies 28 bytes and the optional presentation plan 48 bytes in the 64-bit test executable. The worst supported literal control with seven ten-digit Counts, a maximally escaped reason and the one owner suffix omission emits 636 bytes; the conservative global diagnostic addition is 40 bytes, below the 768-byte wire bound. The complete early human prefix is 497 bytes, below 512. JSON and human are alternative outputs within the existing buffer allowance.

Optional owners stop at the first failed admission. One directly emitted `omissions` record gives the exact retained-minus-shown owner suffix and that first cause (`count_limit`, `byte_limit` or `report_limit`). The mandatory summary remains with empty owners at the exact admitted report cap, where optional wire and scratch are zero. Global diagnostic truncation and deduplicated reasons reflect the omission. The current borrowed reason inventory is at most eight entries: `count_limit`, `byte_limit`, `not_available`, `report_limit`, `location_limit`, `byte_or_count_limit` and `presentation_limit`. One additional owner omission reason needs at most 128 bytes borrowed-vector growth, 128 bytes for a `Value` cell and 16 bytes reason-string capacity, 272 bytes within the 528-byte allowance and 4096-byte additional mandatory ownership share. Reasons are deduplicated before known-length JSON conversion. Admitted optional location limitations use fixed flags; their global reasons and per-location DTO metadata are covered by that owner's optional precharge.

Each optional owner reserves 1024 wire bytes, each reference 2048 and each target 3072, plus 512 per source/effective/related location and six times measured pointer or text bytes. Checked sums refuse unfit owners before constructing DTOs. Scratch reserves 32768 plus eight times the complete owner wire bound, covering nested DTO maps, strings, vector growth, parent serialization and temporary encoding. Actual retained wire size, plus 64 bytes for human row framing, is verified against that admission. Fixed missing/syntax/context conditions use the existing 512-wire/32768-scratch diagnostic admission. Semantic traversal edges, source positions, coordinates, contributor context, record capacities and all four operation counters are precharged before their work or allocation. Semantic failure changes completion; presentation omission does not.

Completion requires every applicable area to be assessed or established not applicable; a definite error can coexist with complete work. Needed acquisition, composition, critical meaning or checking limits leave affected areas undetermined. The advisory area completes its four local proofs when relevant meanings and traversal are established, is not applicable after reliable absence, and is undetermined when needed meaning or work is unavailable. Warnings retain their basis and severity under strict policy. See [initial contradiction advice](initial-advice.md) for guards, witnesses and numeric work.

Declared or specified-default nullable true excludes the first three classes before applicability is recorded. Multiple specific limits still make only the one advisory requested area incomplete. Unavailable meaning and omitted presentation details retain their separate causes; Full includes the same advisory area once.

Reports identify requested inventory, completion within it, and broader coverage separately. Coverage statuses are `assessed`, `not_applicable`, `unassessed`, or `undetermined`; assessed includes findings and does not mean satisfied. Unsupported applicable requested work is incomplete. Excluded initial work is outside that request and appears in broader coverage; it does not alone make the initial incomplete. Adding checks to meet existing inventory obligations is implementation progress. Enlarging membership, guards or semantic scope requires a new assessment/requirement identity. A bug fix may change a result for unchanged input while preserving the advertised meaning; it cannot silently redefine the meaning to match new behavior.

Full content-format rule consultation records `content-format-model-meaning/1`
under the [content-format contract](content-format-contract.md). This records
admitted use independently of successful establishment and optional diagnostics;
it does not expand the existing content-format assessment's scope.

`baseline.interpretations` lists `copied-reference-relocation/1` from
[ADR 0036: Copied reference relocation](adr/0036-copied-reference-relocation.md)
whenever a result relied on it. That is when requested work relocated a copied
reference, read a copied CURIE reference with its authoring document's namespace
mappings, or found that a name reference target in the resolved model differs
from the document as written. The target differs when the written document has
no element at its pointer, when the selected element holds copied content or a
deletion that the written element lacks, or when composition removed the
element the written document has there. A copied CURIE counts even when its
prefix has no mapping in its authoring document. Reports that did none of these
omit the identifier.

`baseline.interpretations` lists `undeclared-extensions-ignorable/1` from
[ADR 0037: Undeclared extension vocabulary](adr/0037-undeclared-extension-vocabulary.md)
whenever a reported conclusion relied on it. That is when Full model meaning,
contextual equality, declared-value consistency, numeric advice or Sample
admission set aside undeclared extension vocabulary in a description and
established its conclusion as if that vocabulary were absent. Recorded
extension vocabulary set aside the same way, such as `oma:id` under
[ADR 0038: Recorded extension vocabulary](adr/0038-recorded-extension-vocabulary.md),
counts too when the report did not consult its recorded registry evidence. That
is the case in a Sample report, in an assessment other than FullBaseline and in a
FullBaseline check that withholds recorded evidence. Where FullBaseline consulted
the evidence, setting the recorded quality aside names nothing. The
[sample contract](sample-contract.md#undeclared-extension-vocabulary) describes
the Sample case. An extension quality that no such conclusion consulted names
nothing. Neither does one in a description whose base meaning is already
stopped, for example by a base quality outside its role. Initial contradiction
advice never consults the vocabulary. Reports that relied on no such description
omit the identifier.

## Outcomes, conditions and truncation

`outcome` contains `complete`, retained aggregate `errors`, `warnings`, `notices`, `incomplete_checks`, `strict_warnings`, and `disposition`. Requested work is complete only when every applicable requested requirement is assessed or established not applicable. Definite errors and scoped incompleteness can coexist. `failed` means an error exists or strict warnings are selected and at least one warning exists; otherwise unfinished work gives `undetermined`; otherwise `passed`. A failed incomplete result keeps `complete:false`. Strict warning policy changes disposition/exit eligibility, not warning severity, condition code, baseline meaning or error count.

Conditions have stable string `code`, severity (`error`, `warning`, `notice`, `incomplete`), basis, requirement/proof identity where applicable, optional primary source/effective/sample location, related locations and bounded structured arguments. Human `message` is explanatory and unstable. Report ordering is deterministic for the same supplied identities/request/version where practical, but consumers must not rely on ordering or wording. Codes are not message templates. For example:

This minimum code catalogue can grow additively with new operation-specific codes. Existing codes keep severity and meaning; changing either allocates a new code. Code parameters grow through optional fields without changing existing parameter meanings. Future codes are handled as strings with an unknown-code fallback; a client must still use structural severity/outcome. Future disposition/severity/basis semantics require a report major version, so a 1.x client can safely classify the fixed values above. The `registration` basis kind is the one exception. It joined version 1.0 in place because no report reader predates the first release, as recorded in [ADR 0038: Recorded extension vocabulary](adr/0038-recorded-extension-vocabulary.md).

The `metadata.info_absent` and `quality.unfamiliar` warnings identify their advice rules with a `basis.id` equal to the condition code and retain the supporting RFC citation. Advice identifiers and citations serve separate roles and can appear together.

Selected civil-value conditions use the domain, severity and basis catalogue in [the civil-time contract](civil-time-contract.md). Actual convention use adds `ADR0018-selected-representation` to the shared interpretation array. Temporal knowledge retains its existing optional shape and records only actual C72 queries. These fields survive optional condition/witness/coverage omission and discarded branch evidence. Declared-value consistency keeps its existing advisory codes and check report shape.

The optional-vocabulary summary's `arguments.observed_occurrences` is a Count of unsupported optional occurrences actually inspected in that source. It is bounded detail and can be absent if the condition is omitted; unfinished checking can leave additional occurrences uninspected. Check reports identify A001 and A002 in `policy.restrictions`, while standalone source inspection applies A002 without assessing SDF vocabulary. The A001 condition keeps its acceptance basis and current Action-input guidance, following [ADR 0008: Reject the historical Action input quality](adr/0008-reject-historical-action-input-quality.md).

Diagnostic count and byte budgets limit detail storage and rendering, not assessment. Aggregate counts and completion are updated before any condition is dropped. `diagnostics` records retained/omitted counts and count/byte/location omission reasons; details can be entirely empty while errors remain nonzero. Aggregate requirement-status and outcome counters remain even when coverage rows/details are omitted. Presentation-only pointer omission or condition truncation leaves otherwise completed checking complete. A semantic ancestry/storage/work limit makes affected requested conclusions incomplete. Rendering never allocates a complete oversized report and cuts it afterward.

## Finite default work and allocation

ADR 0012's input/number defaults remain: 4 MiB per source, 32 MiB catalogue, 256 documents, 64 nested containers, 100,000 JSON nodes per source, 1,024 bytes per number token, 512 coefficient digits, explicit exponent magnitude 1,000,000, and 2,000,000 numeric units per request. The following additional defaults close catalogue/derived/report amplification. They are capability, not standards limits or performance targets.

| Budget | Default / charge before work |
| --- | --- |
| Catalogue parsed nodes | 500,000 total, including opaque content; count every value/container before retaining it. |
| Parsed representation allocation | 64 MiB total reserved allocation, excluding the separately bounded raw source bytes; account strings, maps, arrays, source spans, indices and capacity growth before allocation. |
| Derived effective content | 250,000 retained effective value nodes, 64 MiB total derived representation including ancestry and caches. Charge actual new allocation; shared immutable content charges its owner once. |
| Reference work | 100,000 expansion applications, dependency/effective chain depth 256. Nested path-composition lookups additionally stop at 32 levels, or the reference-depth limit when lower. Charge each expanded application and copied/traversed node; deleted branches need not be expanded. |
| Check/composition work | 10,000,000 units: one per visited value/member/reference edge and one per traversed/copied text/token byte, plus separately metered numeric/pattern work. Charge before traversal/copy; aggregate limits apply across the whole request, not reset for each definition. |
| Ancestry and decoded path tokens | Parent links are retained within the parsed/effective node budgets and their allocation allowances. The parser additionally limits decoded map-key path tokens to 16 MiB. Materialized ancestry and pointer construction consume their applicable work and allocation allowances. |
| Materialized pointers | 8 KiB per rendered pointer, 8 MiB aggregate pointer output/work per operation. Count escaping bytes before allocation; excess is presentation omission where semantic path handles still work. |
| Conditions | 1,000 retained items, 1 MiB total serialized condition detail, 4 KiB message text per item. All larger explanatory collections also consume detail budget. |
| Report | 8 MiB total emitted JSON/human report, including source labels, location strings, coverage detail and escaping. Pre-reserve a bounded mandatory summary/source-identity/status/scope envelope; omit detail before this cap. Never omit aggregate outcome or source attempts. |

Capacity arithmetic is checked. Check work admits effective-result storage before composing the next root. Failed admission retains an `operation.limit` cause at that checked effective root, preserves earlier findings and supplied scope, and contributes to aggregate diagnostics even if detail is omitted. No zero/unlimited sentinel is accepted. Configuration validation enforces finite representable values, supported stack/identity ceilings, and enough report space for the mandatory supplied-source inventory; invalid configurations are request errors before work. Independent definite results and raw retained content survive limits. Builders allow lowering/raising supported budgets, but no public guarantee of accepting every arbitrary usize value exists.

A parser may borrow immutable raw source spans or allocate compact decoded values. Composition may share immutable/COW values or materialize them only after charging nodes, bytes and byte work. Either strategy must obey the same public limits. In particular, a 4 MiB opaque source value expanded thousands of times cannot bypass derived-byte/work budgets merely because its expansion count is under 100,000. Traversing shared content still charges check work. No performance target is invented; ordinary catalogue evidence is structural operation/allocation evidence and a bounded representative timing observation, not throughput qualification.

## JSON report 1.0 and compatibility

The shared check, inspect, sample, author, edit, diff, generate and trace JSON envelope is a single UTF-8 JSON object with `schema:"esdieff.report"`. Required top-level fields are `operation`, `request`, `sources`, `baseline`, `policy`, `outcome`, `coverage`, `diagnostics` and `result`. Check and inspect retain version `1.0`. Sample and author use their distinct version `1.1` payloads, edit adds version `1.2`, diff uses version `1.7` after `1.6`, and generate and trace add version `1.5` below. The [sample contract](sample-contract.md), [authoring contract](authoring-contract.md), [editing contract](editing-contract.md), [revision comparison contract](revision-comparison-contract.md), [generation contract](generation-contract.md) and [trace contract](trace-contract.md) specify these operation payloads without changing check/inspect meanings. A reader rejects an unknown operation before interpreting its result. `request` identifies assessment/inventory identity and scope. `sources` includes every acquisition attempt with role, bounded identity/label and acquisition/decode/content-completeness status and never embeds whole source content. `baseline` identifies actual standards/corrections/interpretations/knowledge. `policy` identifies acceptance restrictions and strict warnings. `coverage` carries requested and broader inventories with aggregate statuses and optionally bounded rows. `diagnostics` carries aggregates, omission reasons and retained conditions. `result` is tagged by operation.

[Check plan runs](check-plans.md), [acquisition receipts](acquisition-contract.md) and [JSON Schema export reports](json-schema.md) use their separate `esdieff.check-run`, `esdieff.acquisition` and `esdieff.schema` identities. The [model reference](model-reference.md) operation emits Markdown. These formats are specified by their own contracts and do not acquire the shared envelope merely because they reuse model operations.

The tables below specify the normative shared check/inspect version-1.0 envelope. Later operation contracts add their own fields and tags. `R` means required; `O` means optional and omitted when absent. Only explicit `T|null` permits null. No absent optional field is interpreted as an assessed result. All maps admit additional optional fields under version-1.x rules, but every listed field retains its meaning/type. `Id` is a nonzero JSON integer from 1 through 256, unique within `sources`; IDs are request-local handles, not durable namespace/content identities. All references must select listed IDs; all source roles share that ceiling. `Count` is a JSON integer from 0 through 4,294,967,295; aggregate counters must not saturate or wrap. The accepted finite-work ceilings guarantee count bounds; configurations that cannot do so are rejected. `Bytes` is a Count measured in UTF-8 bytes except explicit raw filesystem-byte identity. Spans are `[start,end]` Count pairs with start <= end; spans cannot exceed retained source bytes. General JSON model numbers remain exact and are not restricted to Count.

Optional requirement rows have exact retained/omitted counts summing to54; a nonzero omission has one coverage.requirement_rows record with its reason and count. Area rows plus rows_omitted sum to the requested area total. Coverage-only omission also appears in diagnostics.omissions, sets truncated and links its reason in diagnostics.reasons. Consumers compare surviving condition multisets, including codes, bases, arguments, producing IDs and coordinates; duplicate facts cannot stand in for erased facts. Unknown additive fields, row order and human wording do not change meaning. Missing entire optional groups do not imply empty membership or finished per-requirement work. `incomplete_checks` counts each declared requested area once, independently of condition or row retention. Scope IDs and mandatory metadata remain within the original reserve; copied opaque source content is never automatically embedded.

Inspection does not implicitly request a model assessment. Its one declared `inspection` unit covers the acquisition, decoding, selection and, for an effective view, composition required to establish the requested view. Its explicit document selector supplies the root; unrelated candidate failures remain visible without alone making this work incomplete. Inspect outcome.complete is true only when that requested operation is complete, and incomplete_checks counts its one unfinished unit. An available subview does not erase other requested limitations. Broader coverage remains partial/undetermined: source inspection passing establishes a usable requested view, never RFC conformance. A presentation-only omission can produce a partial displayed payload while the operation's semantic work remains complete. If required semantic view establishment is incomplete, the disposition is undetermined unless independent errors or strict warnings already make it failed. The operation tag and count_unit distinguish its one operation from check's declared assessment areas without inventing a standards inventory.

Check result contains no additional payload beyond shared coverage. Inspection result contains a bounded source/effective selected view, explicit partial/unavailable state and explanations; large content is accessed via library-owned source or explicit CLI inspection output, never automatically included in every check report. Sample result contains separate sample source/selector, tagged `admitted`, `rejected` or `undetermined` conclusion and relevant effective model selector/locations. Authoring result contains generated-document identities/content availability, assessment and fidelity state (`established` or `undetermined`); generated bytes are obtained from owned result accessors or an explicit CLI document output. Its generated catalogue supports the same check and inspection operations. Failed or limited authoring never presents a partial candidate as faithfully completed output.

Report wire types are explicit DTOs, independent of Rust struct layout/private graph/enum serialization. JSON null means the explicitly unavailable/absent field defined by its containing tag, never a generic successful default. Version 1.x permits additive optional fields and condition codes; readers ignore unknown fields and retain unknown codes, and handle integer aggregates without lossy floating-point conversion. Existing required fields, fixed outcome/severity/basis/acquisition/decode values, units and absence semantics cannot change within 1.x. Renaming/removal/type changes need a major version. New operations have new tags: a check/inspect reader rejects an unknown operation before interpreting its result. The sample and author tags have their own pinned operation contracts while preserving check/inspect meanings. Rust views/builders use private fields, nonexhaustive extensible result enums and stable accessors; implementation dependencies and storage remain replaceable. Rust source compatibility is maintained for documented public callers within the supported crate version family, with breaking interface changes explicitly versioned independently of the JSON report.

## SARIF projection

`check --format sarif` and `diff --format sarif` emit a SARIF 2.1.0 log for code-scanning annotations, following [ADR 0043: SARIF and Markdown report projections](adr/0043-sarif-and-markdown-report-projections.md). The library gives the same log through `Report::to_sarif(directory)` for a check report and `RevisionComparison::to_sarif(directory)`, where `directory` is the directory relative paths were resolved from. A log projects the same report as the JSON format. It renders only the conditions or differences that report retained and changes no conclusion, disposition or exit code.

The log has one run. `tool.driver` names `Esdieff` and the crate version, and lists one descriptor per result code in `rules` and one per notification code in `notifications`. Each descriptor has the code as its `id` and short description. Its full description names a condition code's severity and basis kind, which the code keeps, or what a diff classification, undetermined reason or warning code means, and its help text points to the contract that describes the codes. `run.columnKind` is `unicodeCodePoints`. `run.originalUriBaseIds` gives `%SRCROOT%` the invocation directory as a `file` URI ending in `/`, when that directory is known. `run.properties` holds the report's `disposition` and the `omittedResults` and `omittedNotifications` counts described below. The one invocation has `executionSuccessful:true`, because the report was produced, and holds the tool execution notifications.

A check result is a retained condition of severity `error`, `warning` or `notice`, at level `error`, `warning` or `note`, with its code as `ruleId` and its message. Errors come first, then warnings, then notes. A retained `incomplete` condition is a tool execution notification at level `warning` instead, with its code as descriptor, because unfinished checking is not a finding about the model.

The physical location of a check result comes from its primary source location, or else from its first related source location, and the other related locations follow in `relatedLocations`. The artifact URI is the source's file path relative to the invocation directory, with `/` separators, percent-encoded segments, `.` and `..` segments resolved as RFC 3986 resolves them, and the base `%SRCROOT%`, so code scanning finds the files when Esdieff runs from the repository root. A path outside the invocation directory, whether absolute or reached through `..` segments, becomes an absolute `file` URI without a base. The region comes from the retained byte span. `startLine` and `endLine` count lines from 1, where CR, LF and CR LF end a line. `startColumn` and `endColumn` count Unicode code points from 1 within the line, and `endColumn` is the column just past the span. `byteOffset` and `byteLength` give the span itself. A location without a span, such as a source that could not be acquired, is a file-level location whose region is only `startLine:1`, because code scanning requires a start line. An effective location becomes a logical location whose `fullyQualifiedName` is the effective pointer, with properties `view:"effective"` and `document`, the label or else the key of its root document. A source without a UTF-8 file path, such as standard input, has no physical location, and its source pointer becomes a logical location with `view:"source"`.

A diff result is a Version warning or a retained difference. Version warnings come first, each at level `warning` with its code as rule, located at the later document's version or the nearest member that would hold it, with the earlier version as a related location. Differences follow in report order. A breaking difference is level `error` with rule `comparison.breaking`, an undetermined one is level `warning` with its reason code as rule, and a compatible one is level `note` with rule `comparison.compatible`. The message names the classification, then the kind, subject, document source key and effective pointer, and the undetermined reason or the Breaking witness with its admissions, in the words the Markdown changelog uses. Every diff result carries `suppressions`. An Acknowledged difference has one suppression of kind `external` with status `accepted`, so reviewers still see the break while code scanning treats it as intended, and the list is empty for every other difference and every Version warning. The later revision's side locates the result when it has a nearest content origin, or when the earlier side has none either. Otherwise the earlier side does, as for a removed definition. The side's origin gives the physical location, and its effective location gives a logical location with the property `revision`. The other revision's side is a related location whose message names that revision.

The log stays within the report byte limit, which it applies on its own, so it can show differences whose details the JSON report left out for space, and the other way around. After the envelope, results and then notifications are kept in order while they fit, and the first that does not fit ends the list. `omittedResults` counts every finding the outcome counts that the log does not show, whether the report or the log left it out: the errors, warnings and notices of a check, and every Version warning and difference of a comparison. `omittedNotifications` counts the incomplete conditions of a check the same way. When either count is nonzero, a final notification at level `warning` states both.

## Markdown changelog

`diff --format markdown` and `RevisionComparison::to_markdown()` give a Markdown changelog of a Revision comparison for release notes, following [ADR 0043: SARIF and Markdown report projections](adr/0043-sarif-and-markdown-report-projections.md). Like the SARIF log, it projects the same report as the JSON format, renders only the differences that report retained and changes no disposition or exit code.

It starts with the title `# Model changes` and a disposition line that counts breaking, undetermined and compatible differences, and the acknowledged ones when acknowledgements were supplied. A `Warnings` section lists each Version warning with the later document, its version or the place it is absent, the earlier version, the breaking count and the code. Sections follow for unacknowledged breaking, unacknowledged undetermined, compatible and acknowledged differences, in that order, and a section without differences is left out. Each item is one list entry naming the kind, the subject, the document's source key and the effective pointer, taken from the later revision's side when it has one. An undetermined item adds its reason and code, and an item with a Breaking witness adds the witness value, its Client direction and both admissions. An acknowledged item starts with its classification.

Model text appears only in code spans, including Given Names in pointers, quality names, source keys and witness values. A span's fence is longer than any run of backticks inside it, and control characters, line breaks among them, become `\uXXXX` escapes, so a name can neither end its span nor start a new block. Reason messages are plain text with Markdown punctuation escaped.

The changelog stays within the report byte limit, which it applies on its own like the SARIF log. Items are kept in order while they fit, warnings first. When any difference or warning is not listed, whether the report or the changelog left it out, a closing line counts them.

## CLI contract

The direct command is `esdieff check [--directory DIR] [--recursive] [--exclude RELATIVE_PATH] [--root INPUT] [--assessment initial-v1|expanded-modified-v1|expanded-units-v1|expanded-content-format-v1|expanded-pattern-syntax-v1|expanded-numeric-v1|expanded-consistency-v1|full-baseline] [--registry-knowledge recorded|withheld] [--strict-warnings] [--format human|json|sarif] [INPUT...]`.

At least one positional INPUT or directory request is required. INPUT is an
explicit file path or `-` for one stdin document. Repeat `--directory DIR` to
prepare model sources from several directories. `--recursive` enables descent
for all supplied directories, and repeatable `--exclude RELATIVE_PATH` omits
literal files or subtrees relative to each directory. These traversal options
require a directory request and apply only to direct checking and `diff`. Plan mode,
`inspect`, `sample`, `author` and `edit` do not accept discovery options. The
[directory discovery contract](directory-discovery.md) defines selection,
ordering, overlap and finite preparation limits.

An explicitly selected root must match exactly one supplied attempt by its
exact native acquisition path. For a discovered root, this is the joined
directory/file path. Directory, positional file and root paths resolve from the
invocation directory. Repeated `-`, unknown or multiply matched roots and
malformed options are usage errors.
Positional files and discovered files are model candidates. Position never
picks the root. Default roots are absent, which requests catalogue scope.
Non-UTF-8 filesystem paths get a safe display label with their distinct identity
preserved. Path labels are not namespace meanings.

The default is initial-v1; expanded-modified-v1 explicitly selects the fixed nine-area inventory, expanded-units-v1 selects the ten-area unit inventory, expanded-content-format-v1 selects the ten-area declaration inventory, expanded-pattern-syntax-v1 selects the fixed nine-area inventory comprising the initial eight plus pattern-syntax/1, expanded-numeric-v1 selects the Initial eight plus advisory-numeric-three/1, and expanded-consistency-v1 selects the unchanged Initial eight plus const-consistency/1 and default-consistency/1, with requested denominator 10. Explicit registry-knowledge values require an expanded unit/content or full-baseline assessment.

For direct checking, successful invocation preparation leads to one requested report on stdout, with a trailing newline. Directory preparation failures exit 2 with stderr and empty stdout before model content or stdin is read. Acquisition and decoding problems are in the ordinary report. Direct-check stderr contains usage errors and output/host failures, not semantic conclusions omitted from JSON. Human and JSON formats use the same outcome/scope/coverage/baseline/policy. Exit 0 is passed requested work, 1 is failed (including strict warnings), 2 is invocation/configuration error, 3 is undetermined work without blocking errors, 4 is inability to emit the requested report or another host operation failure. Failed+incomplete uses 1 and keeps structural incompleteness. Truncated detail alone does not change exit status. stdin is read under input limits; no implicit retrieval/discovery occurs.

A valid [Check plan run](check-plans.md) can instead retain a case-level request error, continue independent cases and emit its run report with aggregate exit status 2. That differs from a whole-invocation error before plan admission, which emits no run report.

`--format sarif` emits the [SARIF projection](#sarif-projection) of a direct check or `diff` report, and `--format markdown` the [Markdown changelog](#markdown-changelog) of a `diff` report, each with the exit code of that report's disposition. Plan mode, `inspect`, `sample` and `trace` refuse `--format sarif`, and every operation other than `diff` refuses `--format markdown`, each with exit 2 and empty stdout.

`esdieff diff --old PATH --new PATH [--recursive] [--exclude RELATIVE_PATH] [--acknowledged FILE] [--format human|json|sarif|markdown]` compares an earlier and a later Model revision and emits one [revision comparison report](revision-comparison-contract.md). Both PATHs are directories or both are files. Each directory is prepared separately with the directory discovery rules, and `--recursive` and `--exclude` apply to both. A document's source key is its path relative to its directory, with components joined by `/`, so documents pair by location. In the two-file form both documents take the key `document` and correspond directly. A file beside a directory, `-` on either side, a missing `--old` or `--new`, a nonexistent PATH, and a relative path that is not UTF-8 or exceeds the 256-byte source key are invocation errors. Standard input is never read. `--acknowledged FILE` may appear once and names a file of Difference acknowledgements. The file is read and decoded before either revision's content, and `-`, an unreadable file and any file the acknowledgement decoder refuses are invocation errors. Both revisions finish preparation before either one's content is read, and both are acquired and compared under one operation allowance. Exit codes follow `check` and the disposition, which only unacknowledged differences decide: a comparison passes with exit 0, an unacknowledged breaking difference exits 1 and otherwise an unacknowledged undetermined one exits 3.

`diff` also accepts `--acknowledgements-output FILE` and `--replace-acknowledgements`. They write the JSON report's eligible acknowledgement entries to a named file for review, following the [acknowledgement export rules](revision-comparison-contract.md#acknowledged-differences). Export preserves the report format and comparison exit status. Existing output requires explicit replacement and cannot alias a selected revision document or supplied acknowledgement file. Invalid destinations and exports the acknowledgement reader cannot accept exit 2 before delivery. Delivery failures exit 4.

`esdieff generate --document MODEL [--kind KIND --pointer POINTER] [--format human|json|jsonl] MODEL_INPUT...` emits the Generated values of one selected description, or of every affordance description of MODEL, as one human report, one [generate report](generation-contract.md#report-15) or [JSON Lines Trace entries](generation-contract.md#json-lines). MODEL, the inputs and `-` follow `esdieff sample`, and `--kind` and `--pointer` come together or not at all. A selector that selects nothing is an invocation error. A generation domain result exits 0 when every selected description completes and 3 otherwise. Invocation errors and host/output failures retain exit statuses 2 and 4.

`esdieff trace --document MODEL --trace FILE [--format human|json] MODEL_INPUT...` checks the Recorded trace FILE against MODEL and emits one human report or one [trace report](trace-contract.md#report-15). MODEL and the inputs follow `esdieff sample`. FILE is a path or `-`, and standard input may be used once across the inputs and the trace. The trace is read before any model input, and a trace that is missing, unreadable or larger than 64 MiB, a line over 1 MiB and more than 100,000 entries are invocation errors. A malformed entry fails only itself. Exit codes follow `check`: 1 for any failed entry, otherwise 3 for any undetermined entry, otherwise 0.

`esdieff inspect --view source|effective --document INPUT --pointer POINTER ...` is a complementary explicit inspect operation using the same report metadata/locations; callers can inspect retained source after assessment failures. Effective inspection never silently falls back to source. Its selector and requested output remain finite. The [sample](sample-contract.md) and [authoring](authoring-contract.md) commands use distinct operation tags and the shared source/report/exit rules, with their selectors, request options and document write/collision behavior specified by those contracts. Authoring's report and document bytes have separate explicit destinations; it never mixes a report and generated SDF on stdout or writes an unasked destination.
